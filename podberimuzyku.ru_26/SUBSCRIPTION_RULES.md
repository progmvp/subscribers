# Правила подписок

## 1. Назначение

Этот документ фиксирует бизнес-правила новой системы подписок Laravel.

Новая цепочка:

```text
Пользователь
    ↓
Выбор тарифа
    ↓
Оплата
    ↓
subscr_payments
    ↓
subscriptions
    ↓
users.subscription_*
    ↓
WordPress 
```
Старая платёжная система WordPress/YooMoney работает параллельно и этими правилами не изменяется.


---

## 2. Тарифы

Пользователю доступны только три основных тарифа:

| Код | Название | Цена | Длительность |
| --- | --- | --- | --- |
| `start` | Стартовый | 250 ₽ | 5 дней |
| `base` | Базовый | 450 ₽ | 14 дней |
| `full` | Полный | 750 ₽ | 30 дней |

Длительность тарифа определяется полем:

```text
plans.duration_days
```

Хардкод длительности тарифов в коде не используется.

### Технический тариф

Тариф:

```text
test
```

имеет следующие параметры:

```text
Цена: 2 ₽
Длительность: 2 дня
```

`test` является исключительно техническим тарифом для разработки и тестирования.

Он:

* не отображается пользователям;
* недоступен для обычной покупки;
* не участвует в правилах выбора тарифа при продлении;
* может использоваться только для технических тестов.

---

## 3. Текущее состояние подписки

Таблица `users` хранит текущее состояние подписки пользователя:

```text
users.subscription_plan
users.subscription_started_at
users.subscription_expires_at
```

Эти поля используются для быстрого определения текущего состояния подписки.

Таблица `subscriptions` хранит историю отдельных периодов подписки.

Таким образом:

```text
users
    ↓
текущее состояние

subscriptions
    ↓
история периодов
```

---

## 4. История подписок

Каждый оплаченный период является отдельной записью в таблице:

```text
subscriptions
```

Основные поля:

```text
id
user_id
plan_id
status
started_at
expires_at
created_at
updated_at
```

Один пользователь может иметь несколько записей `subscriptions`.

Пример:

```text
09.09.2026 15:00 → 23.09.2026 15:00   base
23.09.2026 15:00 → 23.10.2026 15:00   full
```

Это две отдельные записи истории.

---

## 5. Первая покупка

Если у пользователя нет действующей подписки, новая подписка начинается с момента покупки/активации платежа.

Например:

```text
Покупка:
09.09.2026 15:00

Тариф:
base

Длительность:
14 дней
```

Результат:

```text
09.09.2026 15:00 → 23.09.2026 15:00
```

---

## 6. Продление действующей подписки

Если подписка пользователя ещё действует, новый период начинается точно в момент окончания текущей подписки.

То есть:

```text
текущая подписка:
09.09.2026 15:00 → 23.09.2026 15:00

новая покупка:
до окончания текущей подписки
```

При успешной покупке нового тарифа:

```text
новый период:
23.09.2026 15:00 → ...
```

Время не округляется и не пересчитывается от момента новой оплаты.

Сохраняется точный момент:

```text
subscription_expires_at
```

---

## 7. Разрешённые переходы между тарифами

Во время действия подписки пользователь не может перейти на более дешёвый тариф.

### Если текущий тариф `start`

Разрешено приобрести:

```text
start
base
full
```

### Если текущий тариф `base`

Разрешено приобрести:

```text
base
full
```

При этом:

```text
start
```

недоступен.

### Если текущий тариф `full`

Разрешено приобрести:

```text
full
```

Тарифы:

```text
start
base
```

недоступны.

Таким образом:

```text
start → start / base / full

base  → base / full

full  → full
```

---

## 8. Понижение тарифа

Понижение тарифа во время действующей подписки запрещено.

Например:

```text
base
09.09 15:00 → 23.09 15:00
```

Пользователь не может приобрести `start` для продолжения подписки.

Аналогично:

```text
full
```

нельзя продлить тарифом:

```text
base
```

или:

```text
start
```

---

## 9. Полностью истёкшая подписка

После полного окончания существующей подписки пользователь снова может выбрать любой основной тариф:

```text
start
base
full
```

При этом новый период начинается с момента новой покупки.

Исключение составляет тариф `start`, для которого действует дополнительное правило ожидания 24 часа.

---

## 10. Особое правило для `start` после окончания подписки

После окончания действующей подписки тариф `start` становится доступен только через 24 часа после точного момента окончания предыдущей подписки.

Пример:

```text
Текущая подписка:

09.09.2026 15:00
        ↓
23.09.2026 15:00
```

Подписка полностью заканчивается:

```text
23.09.2026 15:00:00
```

До этого момента подписка считается действующей.

После окончания:

```text
23.09.2026 15:00:00
        ↓
24.09.2026 15:00:00
```

тариф `start` всё ещё недоступен.

Начиная с:

```text
24.09.2026 15:00:00
```

тариф `start` снова разрешён.

Таким образом:

```text
23.09.2026 15:00:00
→ подписка закончилась

23.09.2026 15:01
→ start недоступен

23.09.2026 15:30
→ start недоступен

23.09.2026 23:59
→ start недоступен

24.09.2026 14:59:59
→ start недоступен

24.09.2026 15:00:00
→ start доступен
```

Это правило проверяется по точному времени, а не по календарной дате.

---

## 11. Покупка `base` или `full` после окончания

После полного окончания текущей подписки тарифы:

```text
base
full
```

могут быть приобретены сразу.

Дополнительное 24-часовое ожидание относится только к `start`.

---

```text
09.09.2026 15:00
start
5 дней
```

Период:

```text
09.09.2026 15:00
→
14.09.2026 15:00
```

### Пример 2 — `base` продлевается `base`

Текущий период:

```text
09.09.2026 15:00
→
23.09.2026 15:00
base
```

Пользователь покупает `base` заранее.

Новый период:

```text
23.09.2026 15:00
→
07.10.2026 15:00
base
```

---

### Пример 3 — `base` продлевается `full`

Текущий период:

```text
09.09.2026 15:00
→
23.09.2026 15:00
base
```

Пользователь заранее покупает `full`.

Новый период:

```text
23.09.2026 15:00
→
23.10.2026 15:00
full
```

---

### Пример 4 — `base` пытаются продлить `start`

Текущий период:

```text
09.09.2026 15:00
→
23.09.2026 15:00
base
```

Пользователь пытается купить:

```text
start
```

Результат:

```text
ПОКУПКА ЗАПРЕЩЕНА
```

Пока текущая подписка действует, `start` недоступен.

---

### Пример 5 — `start` после окончания

Текущий период:

```text
09.09.2026 15:00
→
14.09.2026 15:00
start
```

`start` снова доступен:

```text
15.09.2026 15:00
```

---

### Пример 6 — после окончания `base`

Текущий период:

```text
09.09.2026 15:00
→
23.09.2026 15:00
base
```

С:

```text
23.09.2026 15:00:00
```

можно приобрести:

```text
base
full
```

`start` станет доступен:

```text
24.09.2026 15:00:00
```

## 13. Точное определение действующей подписки

Подписка считается действующей, если:

```text
subscription_expires_at > текущий момент
```

Если:

```text
subscription_expires_at <= текущий момент
```

подписка больше не считается действующей.

Все проверки выполняются с учётом полного времени:

```text
год
месяц
день
час
минута
секунда
```

Сравнение только по календарной дате не допускается.

---

## 14. Связь платежа и подписки

Новая платёжная таблица:

```text
subscr_payments
```

хранит информацию об оплате.

После успешной активации платежа создаётся соответствующий период в:

```text
subscriptions
```

Поле:

```text
subscr_payments.subscription_id
```

связывает успешный платёж с конкретным периодом подписки.

Логическая связь:

```text
subscr_payments
        ↓
subscriptions
        ↓
users
```

---

## 15. WordPress

Laravel является источником истины для состояния новой подписки.

После успешной активации подписки Laravel передаёт состояние в WordPress через технический API-пользователь:

```text
pmr-api
```

WordPress отвечает за применение соответствующего доступа.

Создание Laravel-пользователей в `wp_users` для этой интеграции не используется.

---

## 16. Старая платёжная система

Существующий WordPress/YooMoney процесс остаётся без изменений.

Не изменяются:

```text
payments
subscr_access_tokens
```

и существующая старая цепочка:

```text
YooMoney
→ payments
→ старый webhook
→ confirm-payment.php
→ WordPress
```

Новая система использует:

```text
subscr_payments
subscriptions
plans
users
```

и работает параллельно со старой.

---

## 17. Автоматическое продление

Автоматическое рекуррентное продление подписки в настоящих правилах не предусмотрено.

Под «продлением» понимается новая покупка пользователем одного из разрешённых тарифов.

```text

          ↓            ↓            ↓
```

```text
                 ПОДПИСКА ИСТЕКЛА
                       │
             ┌─────────┼─────────┐

           start      base      full
             │         │         │

```

## 20. Структура CMS и точка входа пользователя

### 20.1. Расположение систем

В проекте используются две CMS/системы, которые на текущем этапе находятся в разных каталогах сервера.

### Laravel

Основное приложение новой системы подписок:

```text
/var/www/podberimuzyku.ru_26
```

**Laravel отвечает за:**

- пользователей новой системы подписок;
- элемент спискаличный кабинет;
- выбор тарифа;
- создание платежей;
- таблицу `subscr_payments`;
- элемент спискатаблицу `subscriptions`;
- состояние подписки в `users.subscription_*`;
- обработку уведомлений YooMoney;
- активацию и продление подписки;
- правила доступности тарифов;
- передачу состояния подписки в WordPress;
- связь с WordPress через технического пользователя `pmr-api`.

Laravel является источником истины для состояния новой подписки.

---

### WordPress

Текущий каталог действующей WordPress-системы:

```text
/var/www/podberimuzyku.ru
```

**WordPress отвечает за:**

- отображение основного сайта;
- страницы сайта;
- существующий контент;
- существующую систему Members;
- применение ограничений доступа к контенту;
- визуальное размещение формы получения подписки;
- старую платёжную систему, которая на время миграции продолжает работать параллельно.

Текущая WordPress-система не должна создавать пользователей Laravel в таблице `wp_users`.

---

## 20.2. Будущая структура проекта

После завершения миграции WordPress должен быть перенесён внутрь каталога нового Laravel-проекта:

```text
/var/www/podberimuzyku.ru_26/
│
├── app/
├── bootstrap/
├── config/
├── database/
├── public/
├── resources/
├── routes/
├── storage/
├── vendor/
│
└── site_cms/
    └── WordPress
```

Будущее расположение WordPress:

```text
/var/www/podberimuzyku.ru_26/site_cms
```
Таким образом, итоговая структура проекта должна представлять собой:

```text
/var/www/podberimuzyku.ru_26
│
├── Laravel
│   ├── приложение
│   ├── личный кабинет
│   ├── подписки
│   ├── платежи
│   └── API
│
└── site_cms
    └── WordPress
        ├── страницы сайта
        ├── контент
        ├── Members
        └── отображение доступа
```

Перенос WordPress в `site_cms` выполняется после завершения и проверки новой системы подписок и не должен нарушать существующий сайт.

## 20.3. Основная пользовательская страница получения подписки

Пользовательская точка входа в новую систему подписок должна находиться на странице сайта:

```text
https://podberimuzyku.ru/member-subscribers/
```
Название страницы:

```text
КАК СТАТЬ ПОДПИСЧИКОМ?
```
Эта страница является WordPress-страницей.

Laravel не заменяет эту страницу отдельной пользовательской страницей.

## 20.4. Подключение Laravel к WordPress-странице

Форма новой системы подписок должна отображаться внутри WordPress-страницы:

```text
/member-subscribers/
```
Для подключения Laravel используется отдельный WordPress PHP-сниппет.

Сниппет является только интеграционным мостом между WordPress и Laravel.

Он не должен содержать бизнес-логику подписок.

Условная схема:

```text
WordPress
    │
    │  /member-subscribers/
    │
    ▼
PHP snippet
    │
    │  подключение Laravel
    ▼
Laravel
    │
    ▼
SubscriptionController
    │
    ▼
форма выбора тарифа
```
В WordPress-сниппете не должны реализовываться:

- элемент спискарасчёт стоимости подписки;
- определение длительности подписки;
- создание записей в `subscr_payments`;
- создание записей в `subscriptions`;
- изменение `users.subscription_*`;
- активация платежей;
- правила перехода между тарифами;
- обработка **YooMoney**.

Вся бизнес-логика остаётся в Laravel.

## 20.5. Тестовая страница перед переключением

До замены существующей формы новая система должна тестироваться на отдельной копии WordPress-страницы.

Текущая рабочая страница:

```text
https://podberimuzyku.ru/member-subscribers/
```

не изменяется до завершения тестирования.

Создаётся тестовая копия страницы, например:

```text
https://podberimuzyku.ru/member-subscribers-test/
```

На тестовой странице используется отдельный новый WordPress PHP-сниппет, подключающий Laravel.

Старая страница продолжает использовать существующий старый сниппет.

Схема тестирования:

```text
СТАРАЯ СТРАНИЦА

/member-subscribers/
        │
        ▼
старый PHP-сниппет
        │
        ▼
старая система оплаты


ТЕСТОВАЯ СТРАНИЦА

/member-subscribers-test/
        │
        ▼
новый PHP-сниппет
        │
        ▼
Laravel
        │
        ▼
новая система подписок
```

Это позволяет полностью проверить новую систему без риска нарушения работающей старой системы.

## 20.6. Переключение после завершения тестирования

После полного завершения тестирования:

1. Новая форма и Laravel-цепочка должны быть проверены на реальном сайте.
2. Должна быть проверена первая покупка новым пользователем.
3. Должно быть проверено создание пользователя Laravel.
4. Должна быть проверена запись subscr_payments.
5. Должно быть проверено уведомление YooMoney.
6. Должна быть проверена активация subscriptions.
7. Должны быть проверены поля users.subscription_*.
8. Должен быть проверен вход пользователя в ЛК.
9. Должен быть проверен доступ пользователя к защищённому WordPress-контенту.
10. Должно быть проверено окончание подписки.
11. Должно быть проверено продление подписки.
12. Должны быть проверены запрещённые переходы между тарифами.

После этого тестовая форма становится основной.

Целевая страница:

```text
https://podberimuzyku.ru/member-subscribers/
```

Новый Laravel-сниппет заменяет старый PHP-сниппет.

Старый сниппет не удаляется сразу и сохраняется как резерв до окончательного подтверждения стабильности новой системы.

## 20.8. Разделение ответственности
### Laravel

```text
ИСТОЧНИК ИСТИНЫ
```

**Laravel определяет:**

- кто является пользователем новой системы;
- какой тариф куплен;
- сколько пользователь заплатил;
- действительна ли подписка;
- когда она начинается;
- когда заканчивается;
- можно ли приобрести выбранный тариф;
- историю подписок;
- историю платежей;
- состояние доступа.

### WordPress

```text
СИСТЕМА ОТОБРАЖЕНИЯ И ПРИМЕНЕНИЯ ДОСТУПА
```

**WordPress:**

- отображает сайт;
- отображает страницу получения подписки;
- принимает подключение Laravel через интеграционный сниппет;
- продолжает обслуживать существующий контент;
- применяет доступ к защищённому контенту;
- не является источником истины для новой подписки.

## 20.9. Пользователи WordPress

Для пользователей новой Laravel-системы запрещено автоматическое создание соответствующих записей в:

```text
wp_users
```

Например, пользователь Laravel:

```text
user@gmail.com
```

не должен автоматически становиться пользователем WordPress.

Для связи Laravel с WordPress используется технический API-пользователь:

```text
pmr-api
```

и соответствующий REST/API-механизм.


**Логика:**

```text
Laravel User
      │
      │ состояние подписки
      ▼
Laravel
      │
      │ API
      ▼
pmr-api
      │
      ▼
WordPress
      │
      ▼
применение доступа
```

## 20.10. Старая и новая системы во время миграции

На период разработки две системы работают параллельно.

**Старая система:**

```text
WordPress
    ↓
старый PHP-сниппет
    ↓
payments
    ↓
старый YooMoney/webhook
    ↓
WordPress
```


**Новая система:**

```text
WordPress
    ↓
новый PHP-сниппет
    ↓
Laravel
    ↓
subscr_payments
    ↓
YooMoney
    ↓
SubscrSubscriptionService
    ↓
subscriptions
    ↓
users.subscription_*
    ↓
pmr-api
    ↓
WordPress
```

Старая платёжная система не изменяется в процессе разработки новой системы.

Новая система постепенно заменяет только тот функционал, который относится к новой подписке.

## 20.11. Принцип миграции

До завершения миграции:

```text
/var/www/podberimuzyku.ru
```

остаётся действующим WordPress-каталогом.

Новая Laravel-система работает в:

```text
/var/www/podberimuzyku.ru_26
```

После завершения миграции WordPress переносится в:

```text
/var/www/podberimuzyku.ru_26/site_cms
```

Итоговая архитектура:

```text
                         PODBERIMUZYKU.RU
                                │
                ┌───────────────┴───────────────┐
                │                               │
          WordPress CMS                    Laravel
          site_cms/                         /var/www/
                │                         podberimuzyku.ru_26
                │                               │
                │                         ┌─────┴─────┐
                │                         │           │
                │                      ЛК/Users   Подписки
                │                         │           │
                │                         └─────┬─────┘
                │                               │
                │                           YooMoney
                │                               │
                │                         subscriptions
                │                               │
                └──────────── pmr-api ──────────┘
                                │
                                ▼
                       доступ к контенту
```

Главный принцип архитектуры:

```text
- Laravel управляет подпиской.
- WordPress управляет контентом.
- WordPress не создаёт пользователей Laravel.
- Laravel не копирует пользователей в wp_users.
- WordPress получает от Laravel только необходимое состояние доступа.
```
