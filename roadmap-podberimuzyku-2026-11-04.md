# Дорожная карта проекта «Подберимузыку»

**Контрольная точка:** 4 ноября 2026 года\
**Назначение документа:** фиксировать реализованные этапы, текущее
состояние и следующие задачи проекта.\
**Источник актуального кода:** GitHub, репозиторий
`progmvp/subscribers`, ветка `main`.

------------------------------------------------------------------------

## 1. Общая архитектура

-   **Laravel --- личный кабинет и центр управления подписками:**
    пользователи, авторизация, тарифы, сроки подписок и платежи.
-   **WordPress --- источник контента и аудиоматериалов:** отображение
    разделов и проектов, аудиоплееры и защищённый доступ к материалам.
-   Связь Laravel и WordPress реализуется через SSO с одноразовыми
    токенами.
-   В дальнейшем WordPress планируется использовать как временный
    магазин треков, пока разрабатывается собственный `pickup-music`.

## 2. Реализовано

### 2.1. Личный кабинет Laravel и подписки

-   Вход в личный кабинет по одноразовому коду из электронной почты.
-   Вход разрешён для уже существующих пользователей.
-   Личный кабинет отображает сведения о подписке.
-   Реализованы тарифы и сроки действия подписок.
-   Активность подписки проверяется по дате окончания.
-   Реализовано продление подписки из личного кабинета.

### 2.2. Оплата через YooMoney

-   Создание платежа из личного кабинета.
-   Приём уведомлений YooMoney.
-   Обработка успешного платежа и продление подписки.
-   Отправка уведомлений в Telegram.

**Примечание:** старые платёжные механизмы пока не удалены. Их аудит и
очистка запланированы отдельно. Не использовать старую платёжную цепочку
при дальнейшей разработке нового сценария.

### 2.3. Защита аудиоматериалов WordPress

-   Разделены сценарии гостевого и авторизованного доступа.
-   Для блоков похожих проектов настроено ограниченное время
    предварительного прослушивания.
-   Используются защищённые временные ссылки на аудиофайлы.
-   Для гостевого и авторизованного доступа предусмотрены разные сроки
    действия ссылок.
-   Основные аудиоплееры и блоки похожих проектов обрабатываются
    раздельно.

**Известное замечание на будущее:** проверить сценарий, при котором
гостевая защищённая ссылка отсутствует, чтобы исключить возможность
показа исходной полной ссылки на аудио.

### 2.4. Интеграция WordPress и Laravel --- SSO

Реализованы основные механизмы:

-   Laravel остаётся источником истины о состоянии подписки.
-   Laravel создаёт случайный одноразовый SSO-токен.
-   В базе Laravel хранится SHA-256-хеш токена, а не открытый токен.
-   Для токена установлены срок действия и защита от повторного
    использования.
-   WordPress проверяет токен через Laravel.
-   Для SSO используется один технический пользователь WordPress
    `pmr-api` с ролью `subscriber`.
-   Отдельная роль `pmr_api` для этой схемы не требуется.
-   После успешной проверки WordPress устанавливает cookie
    `wordpress_logged_in_...` и подписанную cookie `pmr_sso_access`.
-   Доступ к закрытому контенту проверяется по подписанной SSO-cookie.
-   Гости не должны получать доступ к `wp-admin`; для них предусмотрено
    перенаправление на страницу входа.
-   Кнопка «Перейти на сайт» уже выполняет переход из личного кабинета
    на WordPress.

**Результат последнего теста:** в DevTools обнаружены обе cookie ---
`wordpress_logged_in_...` и `pmr_sso_access`. После входа через Laravel
закрытый контент WordPress открылся. Это подтверждает работу основной
цепочки SSO-авторизации и выдачи доступа.

## 3. Текущая незавершённая задача --- корректный возврат из ЛК

### Что сейчас работает

1.  Пользователь находится на странице раздела WordPress, например ФК.
2.  Нажимает пункт меню для перехода в личный кабинет.
3.  Личный кабинет Laravel открывается в новом окне.
4.  Пользователь входит по коду из электронной почты.
5.  Нажимает «Перейти на сайт».
6.  WordPress открывается, SSO-cookie устанавливаются, закрытый контент
    доступен.

### Что нужно исправить

**Проблема 1. Не сохраняется исходная страница.**

После входа пользователь возвращается на главную страницу WordPress,
хотя переход в ЛК был выполнен со страницы раздела ФК.

Причина, выявленная при анализе текущей реализации: `pmr-return-url.js`
обрабатывает ссылки на `/member-subscribers`, но новая ссылка меню ведёт
непосредственно на `/login`. Поэтому исходный адрес не передаётся и не
сохраняется в этом сценарии.

**Проблема 2. Возврат происходит в окне ЛК.**

Сейчас переход на WordPress выполняется в том же окне, где открыт
Laravel. Требуемое поведение другое: обновить исходную вкладку
WordPress, оставить пользователя на той же странице и закрыть окно ЛК.

### План исправления

#### Часть А. Передача и сохранение исходного адреса

Предварительно затрагиваемые файлы:

1.  WordPress: `pmr-return-url.js` --- передавать URL текущей страницы
    при открытии `/login` в новом окне.
2.  Laravel: `routes/web.php` --- принимать и проверять `return_url`,
    сохранять его в сессии.
3.  Laravel: `AuthController.php` --- обеспечить сохранение адреса
    возврата в процессе входа по OTP.

Адрес возврата должен проходить проверку разрешённых HTTPS-хостов.
Нельзя доверять произвольному URL из параметра запроса.

#### Часть Б. Возврат в исходную вкладку

Предварительно затрагиваемый файл:

4.  WordPress: `pmr-token.php` --- после успешной SSO-авторизации и
    установки cookie обновить исходную вкладку WordPress и закрыть окно
    ЛК.

Если исходная вкладка недоступна или окно нельзя закрыть средствами
браузера, должен оставаться безопасный запасной сценарий --- обычный
переход на сохранённую исходную страницу.

### Критерий завершения

Проверить в чистом браузере:

1.  Открыть страницу раздела ФК.
2.  Нажать пункт меню «ЛИЧНЫЙ КАБИНЕТ».
3.  Убедиться, что ЛК открылся в новом окне.
4.  Войти по одноразовому коду из электронной почты.
5.  Нажать «Перейти на сайт».
6.  Убедиться, что исходная вкладка с ФК обновилась, закрытый контент
    доступен, а окно ЛК закрылось.

После этого повторить проверку для других исходных разделов: ХГ и РС.

**Важно:** не менять уже работающие механизмы SSO-авторизации, проверки
подписки и защиты контента без отдельной необходимости.

## 4. Следующие этапы дорожной карты

Эти задачи не входят в текущую небольшую доработку возврата.

### 4.1. Завершение проверки SSO

-   Полный тест в чистом браузере.
-   Проверка отказа в доступе без активной подписки.
-   Проверка доступа администратора.
-   Проверка сценариев входа, выхода и истечения срока действия
    SSO-cookie.
-   Проверка всех основных разделов и типов закрытого контента.

### 4.2. Очистка WordPress

-   Провести инвентаризацию старых форм, виджетов и механизмов
    авторизации.

    используются.
-   Отдельно провести аудит и очистку устаревшей платёжной логики.
-   Сохранить WordPress как источник контента и аудиоматериалов.

### 4.3. Временный магазин на WordPress

-   Реализовать временную возможность покупки треков на WordPress.
-   Использовать существующую архитектуру Laravel для пользователей и
    подписок там, где это предусмотрено проектом.
-   Не смешивать временный магазин со старой платёжной цепочкой без
    отдельного согласования.

### 4.4. Собственный магазин `pickup-music`

-   Завершить разработку собственного магазина.
-   Постепенно перенести необходимые функции из временного решения.
-   После перехода определить, какие временные компоненты WordPress
    можно окончательно отключить.

### 4.5. Дальнейшее развитие личного кабинета

-   Продолжать централизовать управление аккаунтом, подписками и
    пользовательскими возможностями в Laravel.

## 5. Правила работы с кодом и изменениями

-   GitHub `progmvp/subscribers`, ветка `main`, --- источник истины для
    актуального кода.
-   Перед изменениями сверять файлы с актуальными версиями в
    репозитории.
-   После завершения изменений обновлять соответствующие файлы и ссылки
    в репозитории.
-   При замене кода предоставлять полное содержимое файла либо одну
    точную замену блока --- без разрозненных фрагментов.
-   Не менять работающие части проекта без необходимости и без отдельной
    проверки.
-   Перед существенными изменениями сохранять резервные копии.
-   Проверки базы данных выполнять через phpMyAdmin; WP-CLI на сервере
    недоступен.
-   Тестирование оплаты не должно требовать реального платежа, если
    задачу можно безопасно проверить другим способом.
